# 004. 狭い画面での畳み方

- 状態: 未決
- 起票日: 2026-08-22
- 関連: `scripts/build_site.py` の `STYLESHEET`（マークアップ側は対応済み）
- 暫定実装: あり — 案A相当。表を横スクロールさせている
- プレビュー: `python scripts/build_previews.py` を実行後、`site/previews/index.html` から

## 何に迷ったか

モバイル優先の要件に対し、現在は**表をそのまま横スクロール**させている。
6列あるため、狭い画面では初回・最高・在籍が画面外に出る。

畳み方の定石は3つあり（DP-3.5）、どれを選ぶかは
**利用者が行同士を比べたいのか、1曲ずつ見たいのか**で決まる（DP-3.6）。

- 順位の分布を眺める使い方なら、行が縦に揃っている必要があり横スクロールが向く
- 特定の曲の履歴を確認する使い方なら、1曲ぶんが一度に見える積み上げが向く

この一覧はまだ公開しておらず、**どちらが主になるか観測できていない**。
加えて、順位という「行同士の比較が本質」のデータを扱う一方で、
初回・最高・在籍という「1曲の履歴」も同じ表に載せているため、性格が二つ混ざっている。

## 選択肢

| 案 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| A | 横スクロール（現状） | 行が縦に揃い、順位の比較ができる。実装が最も単純 | 横に隠れた列に気づきにくい。指の操作が縦横で混ざる |
| B | 1曲1ブロックに積み上げる | 1曲の情報が一度に見える。横操作が不要 | 行同士の比較ができない。1画面の曲数が大幅に減る |
| C | 優先度の低い列（初回・最高）を落とす | 縦の比較を保ったまま画面に収まる | 落とした情報に到達する手段が無い（DP-3.10に反する） |

| 案 | プレビュー |
|---|---|
| A | [`site/previews/004-a.html`](../site/previews/004-a.html) |
| B | [`site/previews/004-b.html`](../site/previews/004-b.html) |
| C | [`site/previews/004-c.html`](../site/previews/004-c.html) |

**ウィンドウ幅を 640px 以下にするか、携帯で開くと切り替わる。** 広い画面では3案とも同じに見える。

## 推奨案とその理由

**案A（横スクロール）を維持し、識別子の列を固定する改良を加えることを推す。**

理由は、この一覧が**順位表**だから。順位は行同士を比べて初めて意味を持つ値で、
案Bのように1曲ずつ縦に積むと、順位表としての性格が失われる。
1曲の履歴を見る用途は、P8で作る個別曲ページが本来の受け皿になる。

案Cは画面には収まるが、落とした初回・最高に**到達する手段が無くなる**のが致命的。
畳むことと捨てることは違う（DP-3.10）。展開行を足せば解決するが、
それは案Cではなく別の案（優先度＋展開）になり、実装量も増える。

案Aの弱点は「横に隠れた列に気づきにくい」ことなので、
**曲名の列を固定して横スクロールさせる**と、何の行を見ているか見失わずに済む（DP-3.8）。
これはCSSのみで実現でき、案Aの延長として扱える。

なお、P8で個別曲ページができた後は前提が変わる。
一覧が「探して飛ぶための入口」に寄るなら、案Bを採り直す価値が出る。

## 保留による影響範囲

決めないままでも壊れるものは無い。案A相当の状態が続き、**狭い画面でも全列に到達できる**。

- 影響するのは `build_site.py` の `STYLESHEET` のみ。マークアップは3案すべてに対応済みで、
  各セルは `data-label` と列ごとの class を持っている
- **003（情報密度）と相互に影響する。** 案Bを採ると行の高さの意味が変わり、
  003の結論をそのまま適用できない。003より先に決めるか、同時に決めるのが望ましい
- 002（変動の配色）とも軽く関係する。案Bでは変動が縦に並ばないため、色による塊の把握が効かない
- P8の個別曲ページができると判断の前提が変わる。**今決めても、P8後に見直す前提**で扱うのが妥当
- 案Aの改良（曲名列の固定）は本提案の採否と独立に実施できる。必要なら先行して入れられる
