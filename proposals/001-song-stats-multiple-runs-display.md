# 001. 在籍区間が複数あるときの表示

- 状態: 未決
- 起票日: 2026-08-21
- 関連: `scripts/song_stats.py` の `main()`（`python scripts/song_stats.py <曲名>` の出力）
- 暫定実装: なし（現行動作が案A相当。このルール導入前から同じ挙動）

## 何に迷ったか

`song_stats.py` は1曲の指標を「ラベル : 値」の並びで表示する。他の指標は必ず1行だが、
**在籍区間だけは件数が可変**で、再ランクインを繰り返した曲では何行にもなる。

現状は行ごとにラベルを繰り返している。3区間ある曲の実際の出力:

```
サンプル曲 / サンプル歌手  [X]
  初回ランクイン : 2026-01-01
  最高順位       : 2位 (2026-01-02, 計2日)
  通算在籍日数   : 6日
  在籍区間       : 2026-01-01 〜 2026-01-03 (3日)
  在籍区間       : 2026-01-11 〜 2026-01-12 (2日)
  在籍区間       : 2026-01-20 〜 2026-01-20 (1日)
```

同じラベルが3回出るため、**別の指標が3つ並んでいるようにも読める**。
一方で、区間が1つだけの曲（現在のデータではほぼ全曲）では現状の形が最も素直で、
凝った形にするとかえって冗長になる。1件のときと複数件のときで最適な形が違うのが、
自明に決められない理由。

## 選択肢

| 案 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| A | 現状維持。行ごとにラベルを繰り返す | 実装済み。1区間の曲では最も素直 | 複数区間で同じラベルが並び、別指標に見える |
| B | 最初の行だけラベルを出し、以降は桁を揃えて continuation にする | 繰り返しが消える。1区間なら現状と完全に同じ見た目 | 区間がいくつあるかは数えないと分からない |
| C | 区間数を値として出し、明細を字下げして並べる | 区間数そのものが情報になる（再ランクインしたかが一目で分かる） | 1区間の曲でも2行になる。情報量の割に行数が増える |

案A（現状）:

```
  通算在籍日数   : 6日
  在籍区間       : 2026-01-01 〜 2026-01-03 (3日)
  在籍区間       : 2026-01-11 〜 2026-01-12 (2日)
  在籍区間       : 2026-01-20 〜 2026-01-20 (1日)
```

案B:

```
  通算在籍日数   : 6日
  在籍区間       : 2026-01-01 〜 2026-01-03 (3日)
                   2026-01-11 〜 2026-01-12 (2日)
                   2026-01-20 〜 2026-01-20 (1日)
```

案C:

```
  通算在籍日数   : 6日
  在籍区間       : 3区間
      2026-01-01 〜 2026-01-03 (3日)
      2026-01-11 〜 2026-01-12 (2日)
      2026-01-20 〜 2026-01-20 (1日)
```

## 推奨案とその理由

**案B を推す。**

読み手が困っているのは「同じラベルが並んで別指標に見える」ことで、それは案Bで解消する。
案Bは1区間の曲では現状と1文字も変わらないため、**大多数の曲の見え方を動かさずに問題だけ潰せる**。

案Cの「区間数」は確かに情報だが、通算在籍日数と初回ランクイン日が既にあるうえ、
今のデータは3日ぶんで全曲が1区間なので、**得られる情報より増える行数のほうが目立つ**。
データが数か月たまって再ランクインが普通に起きるようになったら、案Cを採り直す価値がある。

案Cを推すのは、区間数を独立した指標として扱いたい場合。その場合は `summary()` の
戻り値にも区間数を足すのが筋で、表示だけの変更では収まらない。

## 保留による影響範囲

決めないままでも実害は小さい。現状の案A相当の動作が続くだけで、**壊れているものは無い**。

- 影響を受けるのは `scripts/song_stats.py` の `main()` の表示部分のみ、8行程度
- `--json` 出力・各関数の戻り値・テストはこの判断に影響されない。機械可読な側は既に区間の配列を返している
- 現データは3日ぶんで全曲が1区間のため、**今この違いが画面に出ることはない**。
  実際に困り始めるのは、7日以上の空白を挟んで再ランクインする曲が現れてから（最短でも記録開始から8日後）
- 後から変えるのは容易。表示だけの変更で、保存データにも集計にも波及しない
- 他の判断はこれに依存していない。ただし今後 `fetch_log.py` のレポートなど
  「可変長のリストをラベル付きで並べる」場面が出たら、そこでの書式はこの決定に揃えるべき
